# Doctor Role Screen Test Plan

This test plan applies `Screen_Testing_Guideline.md` to the currently implemented doctor area. Test cases are design artifacts only; status is `Not Run` and no Pass/Fail result is claimed.

## 1. Screen Analysis

- **Screen Name:** Doctor workspace: dashboard, today's patients, visit workspace, records, examination, treatment, paraclinical orders/results, visit closing, imaging, appointments, schedule, rooms, notifications, and account.
- **Screen Purpose:** Help an authorized doctor review assigned patient/visit context, record clinical findings, place and review orders, prescribe treatment, schedule follow-up, and complete an eligible visit.
- **Allowed Roles:** Doctor role is indicated by the doctor route group and backend APIs. Exact permission matrix and object ownership rules require confirmation against the approved SRS/permission matrix (`TBD`); UI visibility alone is not evidence of authorization.
- **Preconditions / Entry Points:** Authenticated staff session; doctor profile and any required active assignment; patient profile/visit/order/result exists for the target scenario. Entry points include `/doctor`, `/doctor/today`, `/doctor/visits/{visitId}` and its sections, `/doctor/visit-progress`, `/doctor/imaging`, `/doctor/appointments`, `/doctor/schedule`, `/doctor/rooms`, `/doctor/notifications`, `/doctor/account`.
- **UI Components:** Navigation/shell, dashboard cards, queue/list rows, patient header, tabs/sections, forms and ICD selector, order sheet/table, result panels/dialogs, prescription rows, follow-up dialog, filters/pagination, status badges, confirmation controls, empty/loading/error states, notification and account controls.
- **Field Constraints:** Examination, advice, prescription, order, result assessment, imaging findings/report, and appointment inputs have constraints. Per-field requiredness, lengths, numeric ranges, accepted file limits, and exact date/time rules must come from approved requirements/API contract; unconfirmed values are `TBD`.
- **Business Rules / State Transitions:** Draft/save/submit/complete, order payment/assignment, result availability/review, cancellation/amendment, appointment status, and visit completion/locking are stateful. Expected state transitions must be aligned to the approved UC/BR before execution. Current implementation is evidence for test setup, not authority where requirements are missing.
- **API / Data Dependencies (observed from doctor API client):**
  - Queue/context: `GET /api/v1/appointments`, `GET /api/v1/appointments/{id}`, `GET /api/v1/doctor/visits/active`, `GET /api/v1/visits/{visitId}/exam-queue-entry`; appointment status and care assignment writes use appointment/visit endpoints.
  - Examination/advice: visit examination, examination completion, and after-visit-advice endpoints under `/api/v1/visits/{visitId}`.
  - History and follow-up: patient medical-history read/write, visit past-medical-records, and `/api/v1/visits/{visitId}/follow-up-appointments`.
  - Orders/results: clinic service catalog, visit imaging/laboratory orders and requests, laboratory results/assessment, imaging request/detail/review/findings/report/completion, clinical order/request cancellation, imaging history.
  - Prescription and result sheet: visit prescription read/save/issuance, result-sheets read/regeneration, amendment read/create.
  - Some screens are documented as shell placeholders or backend gaps in `docs/doctor-frontend.md`; do not treat them as fully supported workflows without rechecking current code/API.
- **Risks:** Unauthorized access to patient/visit/order/result; editing or completing a closed visit; duplicate requests from retry/double-click; confusion between draft and final actions; clinical side/laterality mismatch; stale status across screens; API failure displayed as success; privacy leakage in direct URL/API responses.
- **Missing Information / Assumptions:** Doctor-specific UC files and approved permission matrix were not present in `docs/requirements/` during this analysis (only UC01, UC02, UC06, UC10 were found). `docs/doctor-frontend.md` references R3 UC35–UC45, UC49, UC50, UC52 and BR identifiers, but those requirement artifacts were not available in the repository. Confirm required fields, exact statuses/messages, authorization scope, clinical rules, file limits, and performance SLOs before treating corresponding `TBD` expectations as acceptance criteria. `/doctor/imaging`, schedule, account, and notifications are described as shell placeholders in that doc.

## 2. Testing Applicability

| Testing Type | Applicable? | Priority | Reason | Scope |
|---|---|---|---|---|
| Functional Testing | Yes | High | Doctor screens drive clinical documentation and multi-step state changes. | Screen + API + workflow |
| Security Testing | Yes | Critical | Patient health information and clinical writes must be limited by role and object assignment. | UI + API + object-level |
| Performance Testing | Conditional | Medium | Queue/history and clinical APIs matter operationally, but no approved workload or SLO was found. | API/system; thresholds TBD |
| Usability Testing | Yes | High | Clinical values, laterality, workflow state, and final actions must be understandable and recoverable. | UI + representative doctor research |

## 3. Test Data and Execution Notes

- Use synthetic patients, synthetic visits, synthetic orders/results, and dedicated doctor accounts only.
- Prepare: one doctor with an assigned active visit; one visit not assigned to that doctor; one visit in each relevant lifecycle state; imaging and lab orders in pending, result-available, and completed/cancelled states; a prescription draft; a patient with prior completed visits and appointments.
- Replace these fixtures with identifiers from the approved test environment. Do not place real patient information, credentials, or tokens in evidence.
- For security cases, invoke the actual endpoint with the signed-in doctor session and verify persistence/absence of side effects. Exact HTTP code may follow the API contract's anti-enumeration policy; the invariant is no unauthorized data disclosure or mutation.
- Performance thresholds, workload, environment sizing, and availability window are `TBD` until approved. The examples below are not SLA values.
- Tool/Execution values are suggestions, not evidence of execution. All statuses remain `Not Run`.

## 5. Coverage Summary

- **Functional:** Dashboard/queue, examination validation and persistence, diagnosis, locking, clinical orders, duplicate/retry, cancellation, results, imaging, prescription, follow-up, visit completion, API errors.
- **Security:** Unauthenticated access, wrong role, object-level access, finalized records, payload tampering, DICOM access, revoked session.
- **Performance:** Queue/dashboard reads, clinical writes, history pagination, latency resilience. All workload/SLO values remain `TBD` pending approval.
- **Usability:** Patient/laterality recognition, field-level errors, draft/final distinction, feedback/status comprehension, navigation context, keyboard/zoom/responsive checks.
- **High/Critical:** Clinical state transitions, object-level security, finalized-data protection, patient/laterality verification, and core write flows.
- **Manual / environment-dependent:** DICOM viewer, representative-doctor usability sessions, performance workload, session revocation, and object-level authorization.
- **Shared system cases referenced rather than duplicated:** Authentication implementation, transport security, infrastructure soak/stress, generic backup/restore, and clinic-wide audit-log retention. Add references to the system test suite once its IDs are available.
- **Requirements needing confirmation:** Doctor UC/BR source files; permission matrix; required fields and limits; finalization/amendment/cancellation rules; appointment eligibility; exact result/order state transitions; clinical alert semantics; performance SLO and target workload; supported browser/accessibility target.
