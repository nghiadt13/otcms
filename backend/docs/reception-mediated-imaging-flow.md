# Reception-mediated imaging workflow

Doctor submission requires `patientConsentConfirmed: true` on POST `/api/v1/visits/{visitId}/imaging-requests`. The responsible Doctor creates only a Clinical round, orders and idempotency replay; orders start ORDERED / PENDING_PAYMENT. No persistent consent table is introduced.

GET `/api/v1/visits/{visitId}/imaging-orders` reads canonical Clinical orders with round number, snapshot price and optional minimal Diagnostic status via a public batch query. Current-care Doctor authorization precedes reads. Refresh preserves unpaid orders.

GET `/api/v1/reception/clinical-ordering-rounds?page=0&size=20` returns round-oriented Reception work, batching minimal Patient clinical identities, orders and Diagnostic status. Only Receptionists may list or dispatch rounds. Responses are no-store.

POST `/api/v1/clinical-ordering-rounds/{roundId}/invoices` creates/reuses one CLINICAL_ROUND invoice. Billing consumes its own narrow ClinicalRoundBillingPort, implemented in Clinical; it never reads Clinical repositories. Patient identity and one item per non-cancelled order come from Clinical snapshots. No current catalog pricing or client prices. VISIT invoices still require a closed Visit; APPOINTMENT behavior is unchanged. V104 adds an exclusive source FK/check and unique round index, plus room for existing 255-character Clinical service labels.

The existing counter-payment API, verified webhook and reconciliation share updateInvoiceStatus. Only fully PAID invoices propagate round payment in the same transaction. Partial payment leaves orders PENDING_PAYMENT. Full settlement calls the Clinical owner with the exact invoice ordering-round ID; the owner updates only non-CANCELLED orders and flushes those writes before returning, including when joining an outer transaction. The flush does not commit independently: payment, invoice and Clinical updates still roll back together on failure. Repeated settlement and markPaid are safe; cancelled orders stay cancelled and unpaid.

POST `/api/v1/reception/clinical-ordering-rounds/{roundId}/imaging-dispatch` validates every effective imaging order before registration: PAID and ORDERED, or an existing request on retry. All patient/doctor/service/clinical fields come from the order. Diagnostic registration independently checks authoritative paid/open evidence and preserves service-order idempotency. The retired direct Doctor Diagnostic creation service denies calls. Laboratory dispatch is not implemented.

UC28 remains Receptionist-owned. Both unpaid and paid-undispatched ORDERED orders are outstanding. Diagnostic completion evidence still requires completed/released findings and existing Visit audit, cleanup and review notification remain unchanged.

Frontend Billing transport is shared at `src/lib/api/billingApi.ts`; the Billing feature re-exports its existing API to preserve callers. Reception uses the same canonical invoice/counter-payment backend, existing modal/payment layout and stable retry keys. Its clinical orders section is live and round-oriented. No second payment ledger or frontend payment truth is introduced.

## Reception queue room assignment

Dispatch is queue admission, not physical occupancy. The Reception body is `{ "assignments": [{ "serviceOrderId": "...", "roomId": "..." }] }`, with one selected room per new Imaging order. Other patient/Visit/Doctor/service/modality/clinical/payment fields are derived from persisted owner data. A partial round payload may omit already-dispatched orders; it must include all undispatched effective Imaging orders. Duplicate, null, foreign-round or missing assignments fail closed. New work requires ORDERED and PAID.

GET `/api/v1/reception/clinical-service-orders/{serviceOrderId}/eligible-imaging-rooms` and its batch form `/api/v1/reception/clinical-service-orders/eligible-imaging-rooms?serviceOrderIds=<comma-separated UUIDs>` are Receptionist-only and no-store. Batch requests accept up to 200 IDs. Clinical validates each Imaging/ORDERED order and its current open Visit/patient/responsible-Doctor context. Payment is not needed to read options. Visit contexts, canonical Service Catalog facts, Room candidates, current Staff shifts and active Auth accounts are read in batches. Clinical and Diagnostic never query Room/Staff persistence directly.

The Room owner requires active room, IMAGING type, exact `room_supported_services.service_id`, `IMAGING_ROOM`, an active canonical IMAGING service with a supported stored modality (XRAY/MRI/CT/ULTRASOUND), and a current active Imaging Technician. Staff owns profile/account mapping and current shifts (`starts_at <= now`, `ends_at > now`); Auth owns active account/role evidence. No Technician identity is returned to Reception. An occupied room remains a queue option. No free-capacity check, reservation, random/first/least-loaded selection, fixed duration or new reservation model exists in dispatch.

Registration requires non-null roomId and uses `insertAssigned` to persist PENDING/room_id atomically in the dispatch transaction. V097 still enforces one active request per ServiceOrder. Same-room active replay returns the existing request without another insert; different-room replay raises STATE_CONFLICT. Cancelled requests do not satisfy active replay. Call-site audit found no supported positive `insertUnassigned` caller: all fixtures now use explicit assigned registration and direct Doctor creation is retired. The unused insert was removed, and negative Doctor-write assertions now guard `insertAssigned`. The WIP's direct Doctor `create` entry point is already retired/denied and remains unchanged.

Reception displays one selector per paid Imaging order, preselects only a sole option, requires an explicit choice with multiple options, and disables dispatch when any order lacks an option. One action submits all selected pairs. After refresh, Diagnostic's batch status projection supplies the persisted room ID/code/label, including rooms that are no longer eligible for new work. Doctor payment/waiting-dispatch/PENDING/IN_PROGRESS/result/reviewed presentation stays canonical and persistent.

The existing Staff `RoomStatusAccessPort` adapter gates the Technician upload-work/status read: null-room requests stay invisible; only the current active assigned Imaging Technician sees PENDING work. No reservation is needed for this visibility. Doctor queue-room transfer keeps its existing authorization, first-use/version/idempotency/audit checks. A queue-only transfer validates the target queue room and does not release or reserve capacity. Cancellation likewise does not release capacity merely because room_id is set. A separate legacy/manual physical reservation branch is used only when the RoomReservationPort owner explicitly confirms a real reservation exists.

## Separate physical execution-start gap

There is no explicit Technician acquisition-start action completing shared physical room capacity in the current workflow. Existing trusted first-use evidence can advance Diagnostic state; that is not a completed room-capacity integration. Upload/ingestion runtime and physical execution-start capacity remain separate post-dispatch work. This does not block queue admission/visibility.

At that future boundary, canonical Service Catalog values define `startsAt = now`, `expectedEndsAt = now + durationMinutes`, `reservedUntil = expectedEndsAt + bufferMinutes`, and `cleanupBufferMinutes = bufferMinutes`. One shared Room-owned capacity model must prevent overlap with other physical uses; no arbitrary constants or duplicate reservation tables. Resolve ownership/locking/release/cleanup at that boundary. This phase changes neither room reservation schema nor assignment_id ownership. V104 is unchanged; there is no V105.
